[지난 글](/xaler-dev-log/blog/data-brain-console-project-review/)에서는 여러 프로젝트의 기억을 다음 작업으로 이어주기 위해 만든 Data Brain Console을 소개했습니다. 직접 사용해 본 느낌과 몇 차례의 비교 실험을 정리했고, 앞으로는 실제 작업 기록을 더 쌓아보겠다는 이야기로 글을 마쳤습니다.

그런데 그 글을 준비하던 중, 정작 바로 확인할 수 없는 것이 있었습니다.

블로그 원고를 수정하는 작업에도 Console의 맥락이 전달됐습니다. 어디에 초안이 있고, 어떤 말투로 써야 하고, 제가 쓰지 않기로 한 표현이 무엇인지 다시 설명할 필요는 없었습니다. 그래서 자연스럽게 궁금해졌습니다.

**그럼 방금 작업은 얼마나 빨라졌고, 토큰은 얼마나 줄었을까?**

돌아온 답은 아직 비교할 수 없다는 것이었습니다. 이 질문을 계기로, 개인 프로젝트인 Data Brain Console에 일반 작업의 시간과 토큰을 자동으로 남기는 기능을 추가했습니다.

이번 글은 2026년 9월 14일에 진행한 그 작업을 정리한 두 번째 기록입니다. 첨부한 이미지는 당시 화면을 보관한 것이 아니라, 같은 기능이 남아 있는 현재 운영 화면을 10월 20일에 직접 캡처한 것입니다.

## 기록이 있다는 것과 개선됐다는 것은 달랐다

처음에는 작업 시간과 토큰만 확인하면 효과를 알 수 있을 것이라고 생각했습니다. 하지만 Console을 사용한 작업이 3분 걸렸다는 사실만으로는 빨라졌다고 말할 수 없었습니다. Console 없이 같은 작업을 했다면 2분이 걸렸을 수도 있기 때문입니다.

토큰도 마찬가지였습니다. 이전 결정을 바로 전달받으면 다시 찾아보는 과정이 줄어들 수 있습니다. 반대로 필요하지 않은 맥락까지 많이 넣으면 읽어야 할 내용이 늘어납니다. 편리하게 느껴지는 것과 실제 사용량이 줄어드는 것은 별도로 확인해야 했습니다.

당시에는 엄격한 비교 실험용 기록은 있었지만, 평소 하는 작업의 실제 시간과 토큰을 자동으로 쌓는 별도 기록소는 없었습니다. 일반 작업이 끝날 때마다 무엇을 얼마나 사용했는지부터 남길 필요가 있었습니다.

## 측정하려고 매번 LLM을 다시 불러야 할까

기록을 남기자는 방향은 이해됐지만 한 가지가 걸렸습니다.

“측정하려고 매 작업을 다시 평가하면 토큰이 더 많이 드는 것 아닐까?”

제가 원한 것은 평소 작업의 사용량을 확인하는 기능이었습니다. 그래서 이미 Codex가 로컬에 남긴 실행 기록에서 시작과 완료 시각, 모델, 입력 토큰, 출력 토큰과 캐시 입력 토큰을 읽도록 했습니다. JSONL이라는 줄 단위 기록 파일을 프로그램이 읽고 계산하는 방식입니다.

이 파싱과 합계 계산에는 LLM 호출이 없으므로 추가 LLM 토큰이 들지 않습니다. 파일을 읽고 저장하는 로컬 처리 시간은 발생합니다. Console이 원래 작업에 전달하는 맥락도 실제 입력 토큰에 포함됩니다. 따라서 기록 비용이 작다는 이유로 Console 전체가 토큰을 절약한다고 말할 수는 없습니다.

또 하나 신경 쓴 것은 측정 기록의 위치였습니다. 사용량 기록이 다음 작업의 검색 결과와 맥락에 계속 들어가면, 기록을 쌓을수록 프롬프트가 커질 수 있습니다. 관찰 자료는 별도 저장소에 두고 일반 검색과 다음 작업 맥락 후보에서는 제외했습니다.

## 기존 작업 흐름에 관찰 기능을 붙였다

이미 연결해 둔 Codex 훅을 사용했습니다. 훅은 요청을 보내거나 작업이 끝나는 순간에 정해진 처리를 실행하는 연결 지점입니다. 이번에는 그 흐름에 작업별 관찰 기록을 붙였습니다.

1. 요청이 들어오면 프로젝트, 세션과 작업 ID를 연결합니다.
2. 맥락을 준비하는 데 걸린 시간, 추정 맥락 토큰과 포함한 자료 수를 남깁니다.
3. 작업 종료 이벤트가 오면 백그라운드 수집을 예약합니다.
4. 완료된 실행의 시간과 실제 토큰 증빙을 읽어 같은 작업 ID에 연결합니다.
5. 한국시간 날짜 기준으로 일일 요약을 만듭니다.

별도 관찰 저장소에는 요청과 답변 본문을 복사하지 않았습니다. 프로젝트와 작업 식별자, 시간, 사용량과 수집 상태를 남기도록 했습니다. 기존 대화 수집 기능과 사용량 관찰은 저장 목적과 위치를 구분했습니다.

운영 화면에도 자동 관찰 현황을 추가했습니다. 몇 건을 기록했는지만 보면 실제 사용량까지 확보한 것으로 오해하기 쉬워, 완료된 기록과 측정할 수 없었던 기록을 함께 표시했습니다.

![Data Brain Console 운영 설정의 자동 연결과 자동 관찰 상태](/xaler-dev-log/images/data-brain-console-02/automation-status-20261020.png)

*2026년 10월 20일 실제 운영 화면. 캡처 시점에는 관찰 1,805건 중 461건이 완료됐고 1,292건은 측정 불가로 표시돼 있습니다. 전체 관찰 건수가 모두 분석 가능한 기록이라는 뜻은 아닙니다.*

## 캐시와 빠진 측정값을 구분했다

입력 토큰 안에는 이전 입력을 재사용한 캐시 토큰이 포함될 수 있습니다. 그래서 전체 입력과 출력만 합친 수치와, 캐시 입력을 제외한 수치를 따로 볼 수 있게 했습니다.

```text
비캐시 입력과 출력의 합계
= 전체 입력 토큰 - 캐시 입력 토큰 + 출력 토큰
```

예를 들어 입력 1,200토큰, 캐시 입력 800토큰, 출력 300토큰이라면 이 값은 700토큰입니다. 계산을 설명하기 위한 예시이며 실제 성능 결과는 아닙니다. 토큰 합계가 곧 결제 금액은 아니므로 비용을 따질 때는 모델별 요금과 캐시 요금도 따로 확인해야 합니다.

더 중요한 것은 값을 읽지 못한 경우였습니다. 작업 종료 증빙이 아직 없거나 세션 원문을 찾지 못했는데 0토큰으로 채우면, 사용량이 적었던 작업처럼 보일 수 있습니다. 값을 확보하지 못한 기록은 `측정 없음`으로 남기고 원인을 구분했습니다.

실제로 10월 19일 일일 보고서를 확인했을 때는 관찰 17건 중 완료 1건, 대기 5건, 측정 불가 11건이었습니다. 세션 원문을 찾지 못하거나 증빙을 확보하지 못한 항목이 있었고, 보고서에도 측정 상태를 확인해야 한다고 표시됐습니다.

![Data Brain Console의 2026년 10월 19일 일일 관찰 보고서 요약](/xaler-dev-log/images/data-brain-console-02/daily-report-20261019.png)

*2026년 10월 20일 조회한 전날 보고서입니다. 시간과 토큰 통계는 완료된 1건에서 나온 값입니다. 전체 17건의 평균적인 작업 비용이나 Console의 절감 효과로 해석하면 안 됩니다.*

기록 기능을 만들고 나니, 기록을 제대로 확보하는 일도 따로 확인해야 한다는 점이 보였습니다. 지금은 좋은 수치가 나오는지보다 어떤 작업이 측정에서 빠지는지 함께 살펴봐야 합니다.

## 당시에는 어디까지 확인했나

자동 관찰 기능을 붙인 뒤 빌드와 전체 테스트 61개가 통과했습니다. 관찰 저장과 사용량 계산, 일일 요약을 확인했고, Direct 비교가 없는 관찰값이 효율 개선 판정으로 표시되지 않는지도 검사했습니다.

새 빌드를 백그라운드 서비스에 반영하고 전체 최신화를 마쳤을 때, 당시 연결된 프로젝트 12개와 세션 17개가 진단 기준을 통과했습니다. 관찰 기록은 배포 직후 0건이었고 다음 작업부터 쌓이는 상태였습니다. 이 숫자는 9월 14일 구현 당시 결과입니다.

연결을 확인할 때도 서버가 켜졌는지만 보지 않았습니다. 등록한 프로젝트 경로와 세션 근거가 실제 인덱스에서 확인되는지 살펴봤습니다. 다른 프로젝트의 대화를 잘못 이어받으면 사용량을 기록해도 어떤 작업에 쓰인 것인지부터 틀어질 수 있기 때문입니다.

![Data Brain Console 프로젝트의 경로와 연결 세션을 확인하는 실제 진단 화면](/xaler-dev-log/images/data-brain-console-02/connection-diagnostics-20261020.png)

*2026년 10월 20일 현재 Data Brain Console 한 프로젝트의 진단 화면입니다. 당시의 전체 프로젝트 12개 검증 화면과는 다릅니다. `ready`는 등록 근거가 확인됐다는 상태이며 모든 과거 대화가 빠짐없이 수집됐다는 뜻은 아닙니다.*

## 이제 무엇을 비교할 수 있을까

이제 일반 작업에서 얼마나 걸렸고 얼마를 사용했는지 기록할 수 있습니다. 하지만 이 기록만으로 Console 덕분에 빨라졌다고 결론 내릴 수는 없습니다. 비교하려면 같은 요구사항과 시작 코드, 모델 설정을 맞춘 Direct 실행이 필요합니다. 결과물의 품질도 양쪽 모두 확인해야 합니다.

그래서 평소 작업은 한 번만 실행하고 관찰값을 남기기로 했습니다. 효과를 확인할 대표 과제에서는 별도로 Direct와 Console을 비교합니다. 모든 작업을 두 번 실행하면 그 비교 자체에 시간과 사용량이 더 들기 때문입니다.

첫 글에서는 “실제 사용 기록을 쌓아보겠다”고 적었습니다. 그 말을 실행하려다 보니, 우선 제가 보고 있는 숫자가 어떤 작업에서 나왔고 어디까지 믿을 수 있는지부터 정리하게 됐습니다.

지금은 Console을 쓰면서 편해진 부분과, 수치로 확인한 부분을 나눠서 보려고 합니다. 이전 결정을 다시 설명하지 않아도 되는 것은 도움이 됩니다. 그 편리함이 실제 시간과 토큰 절감으로 이어지는지는 비교 기록이 더 쌓인 뒤 이야기하고 싶습니다.

이후에는 이 관찰값을 별도의 모델 추천 모듈과 연결하는 작업도 진행했습니다. 다음 글에서는 그 연결을 다뤄보려 합니다. 이번에 만든 관찰 기록이 어떤 역할을 했는지도 이어서 정리해 보겠습니다.

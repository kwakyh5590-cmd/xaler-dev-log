여러 프로젝트를 오가며 Codex를 사용하다 보면 비슷한 설명을 다시 해야 하는 순간이 생깁니다. 이전에 확정한 결정이 무엇이었는지, 어떤 시도가 실패했는지, 지금도 지켜야 하는 조건은 무엇인지 다시 찾는 데에도 시간이 필요했습니다.

그때 이런 생각이 들었습니다.

**어떻게 하면 매번 처음부터 설명하지 않고, 이전 작업의 판단과 근거를 다음 작업까지 안전하게 이어갈 수 있을까?**

이 질문에서 시작한 프로젝트가 **Data Brain Console**입니다.

Data Brain Console은 회사나 팀에서 진행한 제품이 아니라, 제가 개인적으로 설계하고 개발하며 실제 작업에 사용하고 있는 **개인 프로젝트**입니다. 여러 개발 프로젝트를 더 안전하게 이어가고 반복되는 설명과 확인 과정을 줄이기 위해 만들기 시작했습니다.

## 먼저 결론부터 정리하면

Data Brain Console은 현재 실제로 사용할 수 있는 **개인용 로컬 운영형 MVP**입니다. 개인적으로 사용할 가치는 높고, 여러 프로젝트의 맥락을 다음 작업으로 연결하는 핵심 기능도 작동하고 있습니다.

하지만 새로운 검색 알고리즘을 만든 것은 아닙니다. RAG, 장기 기억, 키워드 검색과 벡터 검색, 작업 추적 같은 기술은 이미 널리 사용되고 있습니다.

제가 이 프로젝트에서 만들고 있는 차이는 각각의 기술보다 **하나의 실제 작업 흐름으로 연결하는 방법**에 있습니다.

- 개인 로컬 프로젝트와 Codex 대화를 함께 연결하기
- 확정된 결정과 나중에 폐기된 결정을 구분하기
- 현재 사용자의 지시를 과거 기록보다 항상 우선하기
- 필요한 근거만 선별해 다음 작업에 전달하기
- 결과가 정말 효율적이었는지 시간, 품질, 토큰으로 검증하기

현재 판단은 명확합니다.

- 개인 실사용 가치: 높음
- 기술 구현 상태: 운영 가능한 MVP
- 검색 기술 자체의 독창성: 낮음
- 작업 연속성과 검증 구조의 차별성: 중상
- 효율 향상 증명: 아직 잠정적
- 외부 판매와 배포 준비도: 낮음
- 계속 운영할 가치: 있음

지금 필요한 것은 새로운 기능을 더 만드는 일이 아닙니다. **1~2주 동안 실제 프로젝트에서 사용한 데이터를 쌓는 것**입니다.

## Data Brain Console은 무엇을 하는가

처음에는 프로젝트 파일과 이전 대화를 잘 검색할 수 있으면 충분할 것이라고 생각했습니다. 그런데 실제로 필요한 것은 단순 검색보다 더 복잡했습니다.

LLM은 코드를 작성하고 판단할 수 있지만, 여러 작업에 흩어진 과거 결정을 항상 정확하게 이어받지는 못합니다.

- 프로젝트별 완료 조건
- 나중에 취소되거나 대체된 지시
- 원본 보존과 사용자 승인 같은 중요한 제약
- 이전 실패 원인과 테스트 결과
- 판단의 근거가 된 파일과 대화 위치
- 지금 가장 먼저 해야 할 다음 작업

Data Brain Console은 이 정보를 찾고 정리해 LLM에 전달합니다. Console이 기억과 근거를 관리하고, LLM은 그 맥락을 바탕으로 판단하고 실제 작업을 수행하는 구조입니다.

즉, 단순한 파일 검색 프로그램보다는 **개인 개발 작업을 위한 로컬 기억 시스템**에 가깝습니다.

## 전체 작업 흐름

현재 구조를 단순하게 표현하면 다음과 같습니다.

```text
로컬 프로젝트, 문서, Codex 대화
        ↓
경로 검사, 안전 정책, 비밀정보 마스킹
        ↓
공통 기록 형식으로 정규화
        ↓
로컬 JSON 저장소와 검색 인덱스
        ↓
키워드 검색, 해시 벡터, RRF 결합
        ↓
현재 요청에 필요한 맥락만 선별
        ↓
Codex 작업에 자동으로 전달
        ↓
작업 결과, 테스트, 변경 내용 기록
        ↓
다음 작업을 위한 상태 최신화
```

### 입력과 원본 보호

등록한 프로젝트 폴더, 코드, Markdown 문서, 데이터와 자산 메타데이터, Codex 최상위 작업 대화, 사용자 메모와 평가 기록을 수집합니다.

이 과정에서 가장 중요하게 생각한 원칙은 **원본을 건드리지 않는 것**입니다. 원본 프로젝트 파일과 Codex 로그는 수정하거나 삭제하지 않고, 검색을 위한 별도의 인덱스만 생성합니다.

경로를 검사하고 심볼릭 링크를 따라가지 않으며, 민감한 파일명과 비밀정보로 보이는 값은 저장 전에 마스킹합니다.

### 저장과 복구

통합 기록, 변경 감사 기록, 해시 벡터 캐시를 로컬 JSON으로 관리합니다. 사람이 직접 확인할 수 있는 프로젝트별 상태 문서는 Obsidian Vault에 생성합니다.

JSON 파일은 쓰기 작업을 순서대로 처리한 뒤 임시 파일과 교체합니다. 백업은 SHA-256으로 무결성을 확인하고, 복구 전에는 별도의 안전 백업을 한 번 더 생성합니다.

### 검색 방식과 한계

검색은 세 가지 방식을 사용합니다.

- 키워드 검색
- `local-hash-v1` 256차원 해시 벡터 검색
- 두 검색 순위를 합치는 RRF 하이브리드 검색

여기서 반드시 구분해야 할 점이 있습니다. `local-hash-v1`은 의미를 학습한 임베딩 모델이 아닙니다. 단어와 문자 조각이 비슷한 자료를 찾는 근사 방식이기 때문에 동의어, 복잡한 문맥, 한국어와 영어가 섞인 의미 검색에는 한계가 있습니다.

검색 결과에는 점수만 보여주지 않고, 왜 검색됐는지와 원문 일부, 가능한 경우 파일과 줄 위치도 함께 표시합니다.

## 요청마다 맥락의 양을 다르게 조절하기

처음에는 관련 자료를 많이 넣을수록 LLM이 더 잘 판단할 것이라고 생각했습니다. 실험 결과는 그렇지 않았습니다.

필요 이상의 맥락은 오히려 작업을 느리게 하고 토큰 사용량을 늘릴 수 있었습니다. 그래서 현재는 요청의 성격에 따라 맥락 예산을 다르게 적용합니다.

- 단순 작업: 약 1,800토큰
- 일반 작업: 약 4,000토큰
- 중단된 작업 이어가기: 약 4,500토큰
- 요구사항 변경: 약 7,000토큰
- 원인과 회귀 진단: 약 8,000토큰

그 안에서도 현재 사용자 지시를 가장 먼저 배치합니다. 다음으로 활성 상태인 확정 맥락, 프로젝트 연속성 문서, 관련 과거 대화와 작업 기록을 넣습니다.

중복되거나 관련성이 낮은 자료는 제외합니다. 이미 대체되거나 종료된 과거 결정은 현재 지시처럼 전달하지 않습니다.

이 부분이 Data Brain Console에서 가장 중요하게 보고 있는 기능입니다. 많이 기억하는 것보다 **지금 필요한 기억을 잘 고르는 것**이 더 중요했기 때문입니다.

여러 코드베이스가 섞인 상위 폴더는 하나의 프로젝트로 취급하지 않았습니다. 안전 크기를 넘는 대용량 세션도 대표 세션 수집에서 제외했고, 원본은 그대로 보존했습니다.

테스트 환경에서 서버 건강 경고가 나타난 경우도 있었습니다. 하지만 직접 로컬 API를 확인했을 때는 정상 응답했습니다. 이 경우 코드 장애라고 단정하지 않고 샌드박스의 로컬 네트워크와 IPC 제한을 따로 구분했습니다.

## 실험에서 확인한 것

현재까지 6개 실험군에서 총 44회의 실행 기록을 남겼습니다. 결과는 한 방향으로만 나오지 않았습니다.

이 글에서 `Direct`는 Console이 준비한 시작 자료 없이 LLM이 코드와 문서를 직접 찾는 방식입니다. `Console`은 작업을 시작하기 전에 Data Brain Console이 고른 관련 맥락을 먼저 전달받는 방식입니다.

v2부터는 두 방식에 같은 요구사항, 완료 조건, 코드 상태, 모델 설정을 적용했습니다. 서로 결과를 볼 수 없는 별도의 코드 복사본과 대화에서 실행했고, 빌드와 테스트를 통과한 경우에만 품질 비교에 포함했습니다. 모델, 실행 시간과 토큰 사용량도 자동으로 기록했습니다.

### 1. 검색 합성 평가

8개 문서와 24개 질문으로 작은 검색 평가를 진행했습니다. 결과는 `Recall@5 87.50%`, `MRR@5 0.8056`이었습니다.

`Recall@5`는 검색 결과 상위 5개 안에 정답 문서가 포함됐는지를 확인하는 지표입니다. 87.50%라는 값은 24개 질문 중 21개에서 정답 문서를 상위 5개 안에 찾았다는 뜻입니다.

`MRR@5`는 정답 문서가 얼마나 앞쪽에 나타났는지를 확인하는 지표입니다. 정답이 1위면 1점, 2위면 0.5점, 3위면 약 0.33점을 주고 전체 질문의 점수를 평균냅니다. 1에 가까울수록 정답이 검색 결과 앞부분에 자주 나타났다는 뜻입니다. 0.8056은 정답을 찾은 경우 대부분 비교적 앞쪽에 배치됐다고 이해할 수 있습니다.

쉽게 말하면, 24개의 질문을 검색했을 때 21개는 상위 5개 결과 안에서 정답을 찾았고 그 정답도 대체로 목록의 앞부분에 나타났습니다.

검색 방식의 방향성은 확인했지만, 실제 프로젝트 검색 품질을 증명한 결과는 아닙니다. 문서 수가 적고 질문마다 정답이 하나뿐이어서 실제 환경보다 쉬운 조건입니다.

### 2. 초기 파일럿 v1

첫 실험에서는 다음 세 가지 기능을 만들게 했습니다.

- 잘못 기록한 평가 실행을 삭제하지 않고 무효 처리하기
- 평가 원본 데이터를 CSV 파일로 내보내기
- Direct와 Console의 실행 시간 차이를 짝으로 묶어 계산하기

각 과제는 Direct와 Console에서 한 번씩, 총 6번 실행했습니다. 같은 과제끼리는 Console이 전달한 맥락 파일을 제외한 시작 코드가 같도록 별도의 복사본을 사용했습니다. 작업이 끝난 뒤에는 제가 직접 빌드와 테스트를 다시 실행했습니다.

세 과제 모두 양쪽에서 품질 기준을 통과했고, Console이 두 과제에서 더 빨랐습니다. 과제별 시간 차이의 중앙값은 약 35초 단축이었습니다.

처음 방향을 확인하는 데에는 도움이 됐지만, 당시에는 정확한 모델 설정과 토큰 기록이 빠져 있었습니다. 그래서 정식 효율 근거로 사용하지 않았습니다.

### 3. Direct와 Console 비교 v2

v2에서는 v1과 같은 세 과제를 다시 실행했습니다. 이번에는 같은 과제마다 코드 상태와 모델 설정을 맞추고, Direct와 Console을 서로 다른 복사본과 대화에서 실행했습니다. 총 3쌍, 6번의 실행에서 모델, 시간과 토큰 기록이 실제 실행 증빙과 일치하는지도 확인했습니다.

품질을 통과한 대응 세트에서 Console이 24초 빨랐고, 첫 시도 성공률은 75% 대 25%였습니다.

반면 이전 응답에서 재사용된 캐시 토큰을 제외하고 새로 처리한 입력과 출력 토큰은 4,466토큰 증가했습니다. 시간과 품질은 긍정적이었지만 비용 효율까지 좋아졌다고 말할 수는 없었습니다.

### 4. Direct와 Console 비교 v3

v3에서는 과제 자체를 바꿨습니다. 빈 맥락 요청을 API, CLI와 화면에서 막는 작업, 프로젝트 연결 증빙을 확인하는 작업, 평가 실행의 상세 증빙을 API와 화면에 보여주는 작업을 비교했습니다. 세 과제를 Direct와 Console에서 각각 실행해 총 3쌍, 6번을 비교했고, 시작 조건과 모델 설정은 같은 과제끼리 동일하게 맞췄습니다.

이번에는 반대 결과가 나왔습니다. Console은 Direct보다 49초 느렸고, 비캐시 입력과 출력 토큰도 6,374토큰 더 사용했습니다.

v2 결과만 보고 Console이 더 빠르다고 결론 내렸다면 놓쳤을 결과였습니다. 시작 맥락을 받았다고 해서 모든 종류의 작업이 빨라지는 것은 아니었습니다.

### 5. 적응형 깊이 v4

v4에서는 모든 요청에 같은 양의 맥락을 주지 않았습니다. CLI 옵션을 추가하는 단순 과제 세 개에는 가벼운 맥락을, 여러 파일을 살펴봐야 하는 회귀 오류 진단 세 개에는 깊은 맥락을 전달했습니다. 같은 여섯 과제를 Direct와 적응형 Console에서 각각 실행해 총 6쌍, 12번을 비교했습니다.

품질을 통과한 5쌍의 중앙값 기준으로 Console이 26.7초 빨랐고, 비캐시 입력과 출력 토큰도 2,947토큰 감소했습니다. 첫 시도 성공률은 83.3% 대 66.7%였습니다.

지금까지 가장 긍정적인 결과지만 아직 전체 계획의 절반인 6쌍만 실행했습니다. Direct 실행 하나는 허용된 경로 밖을 수정해 품질 비교에서 제외했습니다. 지금 숫자만으로 효과가 반복된다고 판단하기에는 이릅니다.

### 6. 맥락 최적화 검증

이 실험은 Direct와 Console의 비교가 아닙니다. Console 안에서 같은 세 과제를 두 가지 맥락 방식으로 실행했습니다. 한쪽에는 최근 대화, 작업 기록과 파일을 정해진 수만큼 고정해서 넣었고, 다른 쪽에는 관련성, 최신성과 자료 종류를 따져 필요한 내용만 골라 넣었습니다. 독립된 복사본에서 총 3쌍, 6번을 실행했습니다.

요청에 맞게 맥락을 선별한 방식이 고정된 맥락을 전달한 방식보다 41.9초 빨랐습니다. 비캐시 입력과 출력 토큰은 4,504토큰, 전달될 것으로 예상한 맥락은 796토큰 감소했습니다.

제가 여기서 확인하고 싶었던 것은 Console의 존재 자체가 아니라, 어떤 맥락을 고르느냐가 실제 작업에 차이를 만드는지였습니다. 결과는 긍정적이었지만 세 쌍만 비교했기 때문에 더 반복해 봐야 합니다.

## 실험을 통해 생각이 바뀐 부분

처음에는 Data Brain Console을 사용하면 작업 속도와 토큰 효율이 자연스럽게 좋아질 것이라고 기대했습니다. 하지만 실제 기록은 그렇게 단순하지 않았습니다.

- 맥락을 많이 넣는 것만으로는 효율이 좋아지지 않았습니다.
- 필요하지 않은 자료는 작업 시간과 토큰을 오히려 늘렸습니다.
- Console이 느리고 비효율적이었던 실행도 분명히 존재했습니다.
- 가장 긍정적인 신호는 Console의 존재 자체보다 정확한 맥락 선별에서 나왔습니다.

그래서 아직 “Data Brain Console을 사용하면 모든 작업이 빨라진다”라고 말할 수 없습니다. 원래 계획한 적응형 실험도 절반 정도만 완료됐고, 여러 실제 프로젝트에서 1~2주 동안 누적한 데이터도 부족합니다.

좋은 결과만 남기면 프로젝트의 실제 가치를 판단할 수 없습니다. 불리한 결과도 보존하고, 품질 기준을 통과한 비교만 근거로 사용하기로 했습니다.

## 실제 작업에서 느낀 장점

이번 블로그 글을 정리하는 작업에도 Data Brain Console의 프로젝트 맥락이 연결됐습니다. 덕분에 다음 내용을 처음부터 다시 설명하지 않아도 됐습니다.

- 원본을 보존하고 안전한 작업 범위에서만 수정하기
- 사용자 지시 없이 작업 범위나 실행 방식을 확대하지 않기
- 오래된 연결 실패를 현재 상태로 오인하지 않기
- 품질을 통과한 대응 세트만 효율 근거로 사용하기
- 다음 단계가 기능 추가보다 실사용 측정이라는 점 유지하기

제가 느낀 실제 이점은 단순히 “예전 대화를 기억해 준다”는 것이 아니었습니다.

- 취소된 과거 지시가 다시 적용되는 일을 줄일 수 있습니다.
- 프로젝트 원본을 잘못 수정할 위험을 낮출 수 있습니다.
- 같은 조사와 상태 확인을 반복하는 시간을 줄일 수 있습니다.
- 여러 프로젝트의 결정이 서로 섞이는 일을 방지할 수 있습니다.
- 결과를 주장하기 전에 근거가 충분한지 확인하게 됩니다.
- 작업이 끝난 뒤 다음 작업에 필요한 자료를 남길 수 있습니다.

## 기존 기술과 무엇이 다른가

RAG, 장기 기억, 지식 그래프, 하이브리드 검색, 증분 인덱싱과 평가는 이미 존재하는 기술입니다. 따라서 “RAG와 그래프를 사용했다”는 사실만으로 이 프로젝트가 새롭다고 말할 수는 없습니다.

Data Brain Console에서 차별화 가능성을 보고 있는 부분은 다음과 같습니다.

- 개인의 실제 로컬 프로젝트와 Codex 대화를 함께 연결합니다.
- 일반 기록과 확정, 대체, 종료된 결정을 구분합니다.
- 현재 지시가 과거 기억보다 항상 우선합니다.
- 프로젝트별 대표 세션만 선택해 다른 프로젝트의 기억이 섞이는 일을 줄입니다.
- 요청 난이도에 따라 맥락 예산을 자동으로 조절합니다.
- 전체 원문을 복사하는 대신 판단 근거가 있는 위치를 유지합니다.
- 외부 API 없이 로컬에서 운영하고 원본은 읽기 전용으로 다룹니다.
- 완료 시간뿐 아니라 품질, 요구 누락, 제약 위반, 재작업과 토큰을 함께 비교합니다.
- 긍정적인 실험과 부정적인 실험을 모두 보존합니다.

즉, 새로운 검색 기술보다는 **개인 AI 작업을 안전하게 이어가기 위한 운영 체계**가 이 프로젝트의 중심입니다.

## 지금 부족한 점

### 1순위: 실사용 효과 증명

12개 연결 프로젝트에서 1~2주 동안 실제 사용 데이터를 쌓아야 합니다. 완료 시간, 맥락 준비 시간, 토큰, 첫 시도 성공률, 요구 누락, 제약 위반과 재작업 횟수를 함께 확인할 계획입니다.

### 2순위: 검색 정확도

현재 해시 벡터를 실제 로컬 임베딩 모델로 교체할 필요가 있습니다. 한국어와 영어가 섞인 실제 질의, 사람이 직접 만든 정답셋, 의미 단락 단위 인덱싱과 최신성 재정렬도 검증해야 합니다.

### 3순위: 맥락 안전장치

필수 작업과 선택 개선을 구분하고, 이미 통과한 테스트를 불필요하게 반복할 때 경고하는 기능이 필요합니다. 시간과 토큰이 일정 범위를 넘었을 때 알려주는 장치도 추가할 수 있습니다.

### 4순위: 데이터 범위

PDF 본문 추출, 이미지 OCR, 대용량 세션 분할 수집과 외부 커넥터는 아직 부족합니다.

### 5순위: 제품화

외부 사용자가 설치해 사용하는 제품으로 만들려면 설치 프로그램, 자동 업데이트, 다중 사용자 권한, 데이터베이스, 장애 복구, 개인정보와 보안 정책이 필요합니다.

현재는 로컬 단일 사용자 도구입니다. 따라서 앱 패키징과 유료 배포를 서두르기보다 실제 사용 효과를 먼저 증명하는 것이 맞다고 판단했습니다.

## 앞으로 확인할 세 가지

지금부터 집중할 부분은 다음 세 가지입니다.

1. 확정된 결정이 다음 작업에 정확하게 전달되는가
2. 요청에 맞게 맥락을 줄였을 때 시간과 토큰이 실제로 개선되는가
3. 여러 프로젝트에서 사용해도 같은 효과가 반복되는가

여기까지 직접 사용해 보니 이 프로젝트를 접을 이유는 없다고 느꼈습니다. 다시 작업을 시작할 때 지난 결정을 찾아주고, 건드리면 안 되는 범위를 알려주는 부분은 실제로 도움이 됐기 때문입니다.

그렇다고 완성된 제품이라고 말하기에는 이릅니다. 아직 모든 작업을 빠르게 만들거나 토큰을 항상 줄여 준다고 자신 있게 말할 만큼 기록이 쌓이지 않았습니다.

지금 제게 Data Brain Console은 여러 Codex 프로젝트의 지난 결정과 근거를 다음 작업으로 이어주기 위해 만든 개인용 로컬 작업 도구입니다. 그리고 정말 시간을 줄여 주는지는 느낌이 아니라 실행 기록으로 확인하고 있습니다.

당분간은 기능을 더 늘리기보다 실제 작업에서 계속 사용해 보려 합니다. 어떤 상황에서 도움이 되고, 어떤 상황에서는 오히려 방해가 되는지 더 솔직하게 기록하는 것이 지금 필요한 다음 단계라고 생각합니다.
